# Admin Panel — React Frontend — Design

**Date:** 2026-08-13
**Status:** Approved (pending user spec review)
**Scope:** Replace the placeholder Mini App page (`admin_panel/static/index.html`) with a real React+TypeScript frontend covering all four admin views — Dashboard, Logs, Memory, Conversations — over the existing read-only `/api/*` backend.

---

## 1. Goal

The admin panel backend has been live and reachable via the Telegram Mini App tunnel since the previous plan (`docs/superpowers/specs/2026-08-13-admin-panel-miniapp-tunnel-design.md`), but the page it serves is a single inline `<script>` that dumps raw `/api/metrics` JSON to a `<pre>`. This plan builds the real frontend: four navigable views, each rendering one or more of the existing API routes in a usable form, opened from the same Telegram menu button that already works today.

This is purely a client built on top of an already-complete, already-authenticated API surface — no backend route changes, no new endpoints, no change to the auth or tunnel mechanics.

## 2. Constraints (from user decisions)

- **All four pages ship together, one spec/plan.** The shared shell (auth resolution, layout, tab navigation, API client) is needed regardless of how many pages exist; splitting into four specs would only multiply process overhead for pages that are each thin over an existing endpoint.
- **Vite build output is served as static files by the existing FastAPI app.** No second process, no dev-server-in-production. `npm run build` writes directly into `admin_panel/static/`, replacing the placeholder `index.html` and adding a hashed `assets/` bundle — the same single-process deploy story the project already has.
- **TypeScript**, for the same reason the Python side is fully type-hinted: the metrics report alone has ~25 fields, and typos in field names should fail at compile time, not render as `undefined` in production.
- **Tailwind CSS + shadcn/ui** for styling — chosen over a hand-rolled CSS approach for faster, more consistent UI across four pages.
- **Tab-based navigation, no router.** A Telegram Mini App webview has no visible address bar for the user to navigate with, so distinct URLs buy nothing; a single `activeTab` state avoids a routing dependency entirely.
- **All four pages poll on a 15-second interval** (not fetch-once, not manual-only) — including Memory/Conversations while a `chat_id` is selected, so an operator watching a live conversation sees it update without manual refresh.
- **Custom fetch/polling hooks, not TanStack Query.** Five simple `GET` endpoints don't justify a caching/retry library and its setup (`QueryClientProvider`, etc.); a ~50-line hook covers polling, cleanup, and dependency-triggered refetch.
- **A dev-mode auth bypass is required**, so iteration doesn't require restarting the bot, standing up the tunnel, and opening real Telegram for every change. It must be structurally incapable of reaching a production build (gated on `import.meta.env.DEV`, which Vite hardcodes to `false` at `vite build` time regardless of what env files are present on disk).
- **Vitest + React Testing Library**, matching the rigor of the Python test suite (447+ tests) rather than shipping this with no automated coverage.
- **File-size rule:** every new/modified file stays ≤ 260 lines, single responsibility — applies to frontend components exactly as it does to the Python backend.

## 3. Architecture

```
admin_panel/
├── frontend/                  # NEW — React+TS source, not shipped as-is
│   ├── package.json
│   ├── vite.config.ts         # outDir: '../static', emptyOutDir: true
│   ├── src/
│   │   ├── main.tsx
│   │   ├── App.tsx             # shell: activeTab state, <Nav>, page switch
│   │   ├── pages/
│   │   │   ├── Dashboard.tsx
│   │   │   ├── Logs.tsx
│   │   │   ├── Memory.tsx
│   │   │   └── Conversations.tsx
│   │   ├── api/
│   │   │   └── client.ts       # fetch wrapper, injects X-Telegram-Init-Data
│   │   ├── hooks/
│   │   │   └── usePolling.ts   # generic poll+cleanup+refetch-on-deps hook
│   │   └── telegram/
│   │       └── initData.ts     # prod: window.Telegram.WebApp.initData
│   │                            # dev:  import.meta.env.VITE_DEV_INIT_DATA
│   └── .env.local               # gitignored, generated by scripts/gen_dev_init_data.py
├── static/                    # BUILD OUTPUT — committed, overwritten by `npm run build`
│   ├── index.html              # replaces today's placeholder
│   └── assets/*.{js,css}       # hashed bundle
├── server.py                  # MODIFIED — mounts /assets as StaticFiles
└── ... (routes/, telegram_auth.py, tunnel.py — all unchanged)
```

**Key points:**

- `admin_panel/frontend/` is a self-contained Node/npm project, isolated from the Python package the way `docs/` or `tests/` are — nothing in the Python backend imports from it.
- There is no build step wired into bot startup or CI in this iteration: an operator runs `npm run build` in `admin_panel/frontend/` and commits the resulting `admin_panel/static/` output, the same way `.env`/`goat2.toml`-adjacent generated artifacts already get committed by hand in this project. Automating this is explicitly out of scope (see §8).
- The only backend change is additive: a new `StaticFiles` mount for `/assets`, alongside the existing unauthenticated `GET /` route — both serve static, non-sensitive content, consistent with `index.py`'s existing exemption from `require_admin_auth`.
- Auth, tunnel, and every `/api/*` route are untouched. This plan is a pure consumer of that existing contract.

## 4. Components

### `admin_panel/frontend/src/api/client.ts` (new)

- A thin wrapper around `fetch`: `apiGet<T>(path: string): Promise<T>`. Injects `X-Telegram-Init-Data` (resolved via `telegram/initData.ts`) on every call.
- Does not throw on a backend-level `{error: "..."}` or `{warnings: [...]}` body (HTTP 200) — those are valid, expected shapes per the existing route contracts (`memory.py`, `conversations.py`, `logs.py`) and are surfaced to the UI as data, not exceptions. Only a non-2xx HTTP status (e.g. `401`) throws.

### `admin_panel/frontend/src/telegram/initData.ts` (new)

- `getInitData(): string` — in a real Telegram webview, returns `window.Telegram.WebApp.initData`. When `import.meta.env.DEV` is true (i.e. running under `vite dev`, never under `vite build`), falls back to `import.meta.env.VITE_DEV_INIT_DATA` if `window.Telegram` is unavailable.
- The fallback branch is guarded by `import.meta.env.DEV`, a compile-time constant Vite replaces with the literal `false` in production builds — dead-code-eliminated from the shipped bundle regardless of what's on disk at build time.

### `scripts/gen_dev_init_data.py` (new, repo-root `scripts/`, Python — reuses the existing signing logic)

- Reads `TELEGRAM_BOT_TOKEN` (`.env`) and `admin_chat_id` (`goat2.toml`), constructs a signed `initData` string using the same HMAC-SHA256 algorithm as `admin_panel/telegram_auth.py::verify_init_data` (shared via import, not reimplemented), writes `VITE_DEV_INIT_DATA=<value>` into `admin_panel/frontend/.env.local` (gitignored, Vite's standard local-override filename).
- Run manually, on demand, whenever the previous fake token expires (`auth_date` older than `max_age_seconds`, default 86400s) or doesn't exist yet.

### `admin_panel/frontend/src/hooks/usePolling.ts` (new)

- `usePolling<T>(fetcher: () => Promise<T>, intervalMs: number, deps: unknown[]): {data: T | null, error: string | null, loading: boolean, refetch: () => void}`.
- Fetches once immediately, then on every `intervalMs`; clears the interval on unmount; tearing down and restarting the interval whenever `deps` changes (e.g. a newly selected `chat_id`), so a stale in-flight poll for the previous selection can't clobber the new one.

### `admin_panel/frontend/src/pages/Dashboard.tsx` (new)

- `usePolling(() => apiGet("/api/metrics"), 15000, [])`.
- Renders the report's fields grouped into cards: cache/prefetch rates, per-tier hit rates, top intents, latency breakdown, token usage, activation-state rates (cold/warm/drift), write-kind counts.

### `admin_panel/frontend/src/pages/Logs.tsx` (new)

- Controls for `level` (`ALL`/`DEBUG`/`INFO`/`WARNING`/`ERROR`), `minutes`, `limit`, held in local state and passed as `usePolling` deps so changing a filter restarts polling against the new query immediately.
- `usePolling(() => apiGet(\`/api/logs?minutes=${minutes}&level=${level}&limit=${limit}\`), 15000, [minutes, level, limit])`.
- Renders `{error}` (backend's own validation failure shape) as a banner if present, otherwise the `lines` array in a scrollable monospace panel.

### `admin_panel/frontend/src/pages/Memory.tsx` (new)

- A sub-selector: **Facts (L1)** / **Working (L2)** / **Episodic (L3)**.
- Facts: `usePolling(() => apiGet("/api/memory/facts"), 15000, [])`, no `chat_id` needed.
- Working/Episodic: a `chat_id` text input; polling only starts once non-empty; `usePolling(() => apiGet(...), 15000, [tier, chatId])`. Episodic additionally exposes the `order` (`recent`/`oldest`) toggle.
- Each tier's `{error: "..."}` shape rendered as a banner, consistent with `Logs.tsx`.

### `admin_panel/frontend/src/pages/Conversations.tsx` (new)

- `usePolling(() => apiGet("/api/conversations"), 15000, [])` renders the chat_id list (`active` / `archived_only` status badge).
- Clicking a `chat_id` selects it; `usePolling(() => apiGet(\`/api/conversations/${chatId}\`), 15000, [chatId])` loads and keeps polling its merged L2+L3 `timeline`.
- Any `warnings` array present on either response (partial-degradation shape unique to this router — see `conversations.py`) renders as a non-blocking banner above whatever data did load.

### `admin_panel/server.py` (modified)

- Add `from fastapi.staticfiles import StaticFiles` and `app.mount("/assets", StaticFiles(directory=STATIC_DIR / "assets"), name="assets")` in `create_app`, alongside the existing `index.router` include. Unauthenticated, matching `index.py`'s existing rationale (static, non-sensitive content).

## 5. Data flow

1. Operator taps the Telegram menu button (unchanged from the tunnel plan) → webview loads `GET /` → FastAPI serves the built `index.html`, which references hashed `assets/*.js`/`*.css`.
2. `main.tsx` mounts `App.tsx`. `App.tsx` resolves `initData` once via `telegram/initData.ts` and renders the default tab (Dashboard).
3. Each page component calls `usePolling` with its own fetcher; `client.ts` attaches `X-Telegram-Init-Data` to every request, exactly as the placeholder did.
4. Backend auth/routing is unchanged: `require_admin_auth` validates the header the same way regardless of which page issued the request.
5. Switching tabs mounts a different page component, which starts its own independent polling; switching away unmounts it, and `usePolling`'s cleanup clears its interval.

## 6. Error handling

| Failure | Effect |
|---|---|
| `/api/*` returns `401` (bad/missing/expired `initData`, or a Telegram user who isn't `admin_chat_id`) | `client.ts` throws; the page renders an auth-error banner instead of its normal content — the same failure the placeholder already surfaced as raw JSON |
| Backend route returns `{"error": "..."}` (HTTP 200) — e.g. Letta or ChromaDB down | Rendered as a banner in place of the data for that specific view; polling continues, so it recovers automatically once the backend dependency comes back |
| Backend route returns `{"warnings": [...]}` alongside partial data (`conversations.py`'s degrade-instead-of-fail routes) | Banner shown above the partial data that did load — never hides successfully-fetched data behind a warning |
| Network failure reaching the panel at all (tunnel down, bot restarted) | `fetch` rejects; `usePolling` surfaces it as `error`, page shows a generic "can't reach the panel" banner; next poll tick retries automatically |
| Dev mode: `VITE_DEV_INIT_DATA` expired or missing | `client.ts` gets a real `401` from the real backend, surfaced the same as any other auth error — operator re-runs `scripts/gen_dev_init_data.py` |

No error path is fatal to the whole app — each page owns its own request lifecycle, so a failure on one tab never affects another.

## 7. Testing

- `usePolling` — fake timers (Vitest): asserts immediate fetch, interval refetch, cleanup on unmount, restart on `deps` change, no overlapping intervals.
- `client.ts` — asserts the `X-Telegram-Init-Data` header is attached, a non-2xx status throws, a 200 with `{error}`/`{warnings}` resolves normally (not as a thrown error).
- Each page component — rendered with a mocked `client.ts`, fake data matching real API shapes (copied from the existing Python route tests' fixtures where practical): asserts normal-data rendering, `{error}` banner rendering, `{warnings}` banner-plus-partial-data rendering, and (for Logs/Memory) that changing a filter/selector triggers a new fetch.
- `initData.ts` — asserts the dev-mode branch only activates when `import.meta.env.DEV` is true and `window.Telegram` is absent; asserts production path reads `window.Telegram.WebApp.initData` directly.
- No test touches a real network call, a real `cloudflared` tunnel, or the live bot — consistent with the project's local-fakes-only testing convention.

## 8. Out of scope (this iteration)

- Automating the `npm run build` → commit step (e.g. a pre-commit hook or CI job) — done by hand for now, same as other generated/local-only files in this project.
- Any write/mutating UI — the panel stays read-only, unchanged from the base admin-panel design.
- Real-time push (WebSockets/SSE) — 15-second polling was the explicit choice over anything more elaborate.
- Deep-linking or browser back/forward — no router, by design (§2).
- Telegram `BackButton`/native theming beyond basic Tailwind styling — not requested.
- Auto-refreshing `VITE_DEV_INIT_DATA` — the dev script is a manual, on-demand tool, not a running watcher.

**How to apply:** This is a pure frontend addition over an already-complete, already-authenticated backend — no `/api/*` route changes. Every page follows the same `usePolling` + banner-on-error/warning pattern, so a reviewer checking one page checks the shape of all four. See [[admin-panel-miniapp-tunnel-design]] (`docs/superpowers/specs/2026-08-13-admin-panel-miniapp-tunnel-design.md`) for the auth/tunnel mechanics this consumes unchanged, and [[admin-panel-design]] (`docs/superpowers/specs/2026-08-13-admin-panel-design.md`) for the original `/api/*` route contracts.
